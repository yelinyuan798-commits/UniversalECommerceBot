# 平台接入与真实店铺验收

先把商品资料和服务规则填进工作台，再用几条模拟咨询检查回复。正式连接店铺后，机器人按商品回答常见问题、按授权价格报价，并把售后或不确定的问题交给店主处理。

第一次使用，先走“本地体验”即可：**不需要店铺登录，也不需要 AI 密钥。** 商品配置与平台接入是两件事；商品规则可以一键生成，自己的店铺仍需完成登录与页面适配。

- **先体验**：[下载安装](#安装与启动) → [添加商品并试聊](#先体验商品客服)。
- **正式使用**：[连接店铺](#正式连接店铺) → [测试买家验收](#验收标准) → 日常查看消息与人工接管。
- **接入人员参考**：[平台状态](#当前接入边界)、[官方能力](#官方能力核查)、[网页参数](#浏览器适配器配置)。

## 安装与启动

需要先安装 Python 3.11 或更新版本。Windows 安装 Python 时启用“Add Python to PATH”，以便安装脚本找到 Python。

1. 打开 [项目 GitHub 页面](https://github.com/yelinyuan798-commits/UniversalECommerceBot)，点击 **Code → Download ZIP**，下载后解压。后面的脚本都在解压后的项目文件夹中运行；不要直接在压缩包内启动。
2. **首次安装**：Windows 双击 `setup.bat`；macOS / Linux 在项目文件夹打开终端，运行 `bash setup.sh`。脚本会创建运行环境、安装依赖并下载 Chromium，等待出现安装完成提示。
3. **日常启动**：Windows 双击 `start.bat`；macOS 可以双击 `start.command`，或在终端运行 `bash start.command`。Linux 使用 `bash start.command`。
4. 浏览器未自动打开时，手动访问 `http://127.0.0.1:8765`。这是本机工作台地址。

安装只需在首次使用或更新依赖后执行；平时直接运行启动脚本即可。macOS 如果提示文件没有执行权限，可以始终用 `bash start.command`，也可以先运行 `chmod +x setup.sh start.command`。

专用浏览器的登录资料和聊天记录保存在项目的 `data/` 目录；Chromium 程序由 Playwright 下载到系统缓存，二者不是同一目录。使用网页接入的平台时，请在机器人打开的专用浏览器中完成登录；闲鱼协议接入使用本机保存的登录资料。

## 先体验商品客服

1. 在 **“商品与规则”** 填写店铺、商品名称、“商品所属平台”和“平台商品 ID”，然后填写标价、最低可接受价格、库存、发货规则及常见问答。首次体验可以用自己的样例资料；正式接店前必须改为真实商品信息。
2. 点击 **“一键生成并保存配置”**。售价、底价、是否议价和转人工关键词使用对应字段控制。“定制条件”里独立一行“不议价”可以生成禁止议价规则；其他自由文字不会自动变成任意业务操作。
3. 在右侧 **“先试着聊一聊”** 选择“咨询商品”，点击 **“问价格”**、**“试议价”**、**“问发货”**，也可以自行输入问题。这里的消息只在本机测试，不发送给真实买家。
4. 输入“转人工”检查接管行为。试聊会话暂停后，点击 **“重新开始一个会话”** 继续测试。

**添加第二件商品**：在表单中填写另一组“商品所属平台＋平台商品 ID”及资料，再点击“一键生成并保存配置”，新商品会加入列表；同一平台、同一商品 ID 则更新已有资料。保存后在右侧“咨询商品”中选择要测试的商品。需要批量调整时，再展开 **“多商品 / 精细编辑”**，修改后点击 **“保存完整配置”**。

同一商品 ID 在不同平台可以分别设置资料和价格；平台专用配置优先于“所有平台共用”。正式使用时，商品 ID 必须与商家页面实际识别到的商品一致。

无需模型密钥即可使用规则和已配置问答。需要可选 AI 能力时，只在本机 `config/.env` 配置模型服务。商品资料保存在 `config/merchant.json`，平台设置保存在 `config/platforms.local.json`，均属于本机私有配置，不提交到 Git。

## 正式连接店铺

开始前，准备一个商家账号和一个专用测试买家账号。先在 **“平台接入”** 配置目标平台；当前页面使用配置编辑框，没有“填商品描述就自动登录所有平台”的功能。

- 将目标平台的 `enabled` 设为 `true`，暂时保留 `dry_run: true`，其余平台保持原设置。
- 闲鱼登录资料只在本机 `config/.env` 配置。
- 网页平台需要自己的客服消息页地址和可靠的页面映射；公共模板中的选择器默认留空，不能直接复制测试页面的标识使用。由熟悉该商家页面的人按[网页参数说明](#浏览器适配器配置)完成适配。

接下来按以下顺序操作：

| 步骤 | 在工作台怎么做 | 此时应确认什么 |
| --- | --- | --- |
| 1. 保存接入 | 点击 **“保存接入配置”** | 目标平台已启用，仍处于 `dry_run: true` |
| 2. 观察真实新消息 | 点击 **“开始观察”**；网页接入时在弹出的专用浏览器完成登录，再让测试买家发送新问题 | 识别到的买家、会话、商品正确，候选回复符合规则；此时不会发送 |
| 3. 停止观察 | 点击 **“停止”** | 当前运行已停止；运行中不能直接切换启动模式 |
| 4. 允许目标平台发送 | 将该平台 `dry_run` 改为 `false`，再点击 **“保存接入配置”** | 只修改准备实测的平台；其他平台可继续保留 `dry_run: true` |
| 5. 开启自动回复 | 点击 **“开启自动回复”**，确认提示，并检查平台连接状态 | 全局自动回复模式已开启，且目标平台允许发送 |
| 6. 确认实际收件 | 让测试买家再发送一条**新消息**，到买家端检查回复 | 收到一次正确回复；再按[验收表](#验收标准)逐项检查 |

观察期间已经见过的消息不会切换后补发。因此第 6 步必须发送新消息；不要通过删除去重数据库重试，否则可能向顾客重复回复。

日常在 **“消息与人工接管”** 查看回复状态和待处理会话。需要店主处理的会话会暂停自动回答；店主处理完后，点击 **“恢复自动回复”**。需要整体暂停机器人时，点击顶部 **“停止”**。

## 官方能力核查

以下是 2026-11-02 核查的官方公开文档；具体账号当前可获得的权限以平台控制台为准。

- 淘宝存在官方机器人下发接口 [`taobao.message.chatrobot.async`](https://developer.alibaba.com/docs/api.htm?apiId=48631)。文档要求用户授权，并使用平台颁发的 `request_token`；请求头中的 `request_id`、`tenant_id`、`action_mode` 来自上行事件。因此只知道接口名称或持有普通网页 Cookie，不等于已经具备完整机器人收发权限。
- 淘宝的[智能客服咨询商品接口](https://developer.alibaba.com/docs/api.htm?apiId=54107)标注需要授权，并要求在聚石塔内调用。不要把公开商品页查询与商家客服商品上下文混为一谈。
- 京东官方列有[咚咚机器人 API 类目](https://jos.jd.com/apilist?apiGroupId=3834&apiGroupName=B2C-%E5%AE%A2%E6%9C%8D-%E6%9C%BA%E5%99%A8%E4%BA%BA-%E5%92%9A%E5%92%9A1.0)。公开目录不足以确认本店铺已取得某个接口权限。
- 京麦 [JSSDK 的 `sendDongdongMsg`](https://jmw.jd.com/docs/jssdk/jssdk-mobile/api.html)限定在由咚咚启动的插件页面内使用，目标是当前聊天用户，不能当作通用服务端消息发送 API。
- 京东[商家咚咚官方下载页](https://im.jd.com/seller/download/)提供 [Web 入口](https://dongdong.jd.com/)。是否能接待客户还取决于登录账号及客服权限。

本版本没有把未取得授权、未联调过的官方 API 包装成已可用接口。若店铺已有官方机器人资质，可以保留客服核心，另写接收上行事件、验签和调用授权下发接口的适配器。

## 浏览器适配器配置

在对应平台配置的 `config` 对象中填写浏览器参数，平台顶层保留 `dry_run: true`。下面展示字段格式；`[data-*]` 是本地测试页面的约定，**不是淘宝、京东或其他平台的通用网页选择器**，必须根据当前商家页面逐项替换。

```json
{
  "dry_run": true,
  "config": {
    "url": "https://dongdong.jd.com/",
    "profile_dir": "data/browser/jd-test-shop",
    "headless": false,
    "poll_interval": 2,
    "process_existing": false,
    "selectors": {
      "ready": "[data-workbench-ready]",
      "conversation": "[data-active-conversation]",
      "conversations": "[data-conversation-entry]",
      "messages": "[data-message-id]",
      "message_text": ".message-text",
      "composer": "textarea",
      "send": "button.send"
    },
    "attributes": {
      "conversation_id": "data-conversation-id",
      "user_id": "data-user-id",
      "item_id": "data-item-id",
      "message_id": "data-message-id",
      "direction": "data-direction",
      "delivery_status": "data-status",
      "message_timestamp": "data-timestamp"
    },
    "inbound_value": "inbound",
    "outbound_value": "outbound",
    "sent_values": ["sent", "delivered"]
  }
}
```

选择器使用标准 CSS 语法，不使用 Playwright 专用的 `text=` 或 `:has-text()`。字段需要满足以下条件：

- `ready` 只在已登录、可接待状态下出现。不能用登录页也存在的 `body` 之类元素代替。
- `conversation` 必须唯一指向当前会话面板，该面板必须携带可靠的会话和买家标识。商品标识对应商家配置中的产品。
- `messages`、`message_text`、`composer`、`send` 都在当前会话面板内查找，避免匹配到其他聊天窗口。
- 每条消息必须有稳定的 `message_id` 和明确的收发方向，只有等于 `inbound_value` 的消息可以触发回复。不能用行号、显示时间或聊天文本代替稳定消息 ID。
- `delivery_status` 指定发出的消息状态属性，只有等于 `sent_values` 中明确成功状态的回显才记为发送成功。仅出现消息气泡但无法确认状态时记为 `unknown`，需要人工核实，不自动重发。
- 可选的 `conversations` 用于切换会话列表；各行必须有对应的 `conversation_id`。未配置时只处理当前打开的会话。
- `message_timestamp` 必须对应每条消息的可靠创建时间，值可以是 Unix 秒 / 毫秒或带时区的 ISO 8601 时间。自动回复模式下，缺少有效时间的消息会被跳过并提示校准；明显来自未来的消息也会跳过。不要用页面渲染时刻代替消息创建时刻。
- `process_existing: false` 是默认值，跳过当前连接启动之前的消息；启动后新买家第一条带有效时间的咨询会正常处理。`true` 会允许处理历史消息，只能在明确需要补处理的测试场景使用。
- `profile_dir` 为专用目录，每个商家账号单独使用，不能多个浏览器进程并发打开同一目录。

若真实页面没有可稳定获取的会话 ID、买家 ID、消息 ID、创建时间、方向或发送状态属性，当前适配器不能直接启用；需要先针对该页面补充可靠的提取方式，或接入获授权的官方机器人接口。不要填假的标识来绕过检查。

## 真实店铺的准备

1. 在本机准备商家账号和一个独立的测试买家账号。不要使用正在服务的真实顾客来验证发送。
2. 在机器人专用浏览器目录登录工作台，完成平台正常登录与验证。登录状态只保留在本地，不放入 Git，也不发到聊天、工单或截图中。
3. 商品 `id` 填实际平台商品标识，价格、库存、发货与售后规则填商家确认的数据。没有填写的事实应转人工或询问，不能据商品名编造。
4. 先以预览模式观察读到的买家、会话、商品、消息方向与建议回复。预览通过后才启用实际发送。
5. 每个平台和店铺分别保留配置及验收记录。页面改版、账号切换或客服权限变化后重新验证。

## 验收标准

| 检查 | 操作 | 通过标准 |
| --- | --- | --- |
| 单条收发 | 测试买家咨询已配置商品 | 商家端识别正确，买家端收到一次正确回复 |
| 收件人隔离 | 两个买家同时咨询不同商品 | 回复分别送达对应会话，无跨会话商品信息 |
| 自身消息 | 商家手动发送消息 | 机器人不回复自己、不产生循环 |
| 历史消息 | 打开已有会话、刷新页面 | 历史记录不被当作新咨询批量回复 |
| 新买家首条 | 启动后让新的测试买家首次咨询 | 第一条咨询正常识别，不能误判为历史 |
| 观察切实发 | 观察一条消息，切换模式，再发新消息 | 旧观察消息不补发，新消息正常发送 |
| 重连与重启 | 同一消息重复推送，重启程序 | 不重复发送已处理回复；发送状态可追踪 |
| 发送失败 | 断网或让发送按钮不可用 | 不把失败或未知结果写成已送达，不盲目重发 |
| 会话切换 | 生成回复过程中切换聊天对象 | 不向新聊天对象发送旧回复 |
| 登录失效 | 退出工作台登录 | 停止发送并提示重新登录 |
| 页面变化 | 改动测试页面必要标识或选择器 | 停止自动发送，不能猜测收件人 |
| 价格规则 | 反复压价至低于商家底价 | 报价不低于设置底价 |
| 未知信息 | 咨询未配置规格或未知商品 | 询问或转人工，不编造规格、库存或承诺 |
| 人工接管 | 触发售后 / 投诉 / 人工关键字 | 记录待人工处理，会话暂停自动回答，人工恢复后再接待 |
| 长时间运行 | 对测试账号持续运行并断网恢复 | 留下运行时长和错误记录；短测不能宣称 7×24 稳定 |

记录每个真实测试的平台、日期、工作台版本/页面、测试场景、结果和必要的脱敏证据。凭据、买家个人信息和完整会话记录不应提交到公开仓库。

## 测试结果的含义

- 单元测试：验证商品规则、去重、状态与异常处理。
- 本地浏览器端到端测试：在项目自带的模拟商家页面验证读取、决策、输入、点击发送及防重复流程。
